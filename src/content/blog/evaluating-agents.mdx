I gave a talk at [Digital Jungle](http://luma.com/qdl9mr2e?tk=P3UvLA) in early 2026. Not to pitch something new, just to map the last few years of evals. I'd spent late 2025 building [Manus](https://manus.im), an agent that ran multiple turns and edited real code. Before that I wrote [Building Reliable LLM Applications](/blog/building-reliable-llm-applications): RAG, structured outputs, single-turn stuff. That post still holds. It's August 2026 now. This is a quick thought about how things have changed.

The difficult challenge has now shifted to finding the right problem for LLM evals. We used to struggle to get a model to pick the right letter on a quiz. Now the models crush those quizzes, and the work is deciding what "pass" even means when the thing you're measuring can run for forty turns, call tools, and leave a database in the wrong state.

We still treat the LLM as a function. You throw something in, you get something out, you compare. What changed is the scope of what we can throw at that function, and how the model itself is trained. Evaluating a model (question in, letter out) is not evaluating an agent (trajectory, tools, environment state).

[Shunyu Yao](https://ysymyth.github.io/The-Second-Half/) called this AI's halftime. First half: invent better training methods. Second half: define the right problem. I buy that.

## How we got here, quickly

Training used to be next-word prediction. In 2019, [OpenAI trained GPT-2](https://openai.com/index/better-language-models/) "simply to predict the next word in 40GB of Internet text" and would not release the full weights. The evals matched that job: finish a sentence, pick a letter.

Then the recipe got bigger. Scale. Then [o1](https://openai.com/index/learning-to-reason-with-llms/) in September 2024: reasoning trained in with RL, not just prompted. OpenAI's point was that accuracy goes up if you spend more compute at test time, not only at train time. On the 2024 AIME, GPT-4o averaged 12% (1.8/15). o1 averaged 74% with one sample and 83% with consensus among 64 samples. Same function call. More thinking inside it.

Evals followed the same curve. LAMBADA and MMLU asked for a word or a letter. SWE-bench asked for a patch in a real repo. Devin showed that wrapping the model in a harness (shell, editor, retry) is a different measurement than a single completion. Claude 3.7 Sonnet plus Claude Code later reported 70.3% on SWE-bench Verified. Then τ-bench stopped scoring the prose and started scoring the database.

```
LAMBADA / MMLU     next word or a letter
SWE-bench          issue in, patch out, tests compare
Devin (Mar 2024)   same dataset, now a tool loop
o1 (Sep 2024)      train the thinking, not just the next token
70% on Verified    then tau-bench scores the database
```

That's the whole map. Same `f(x) -> y`. The `x` got a lot larger.

## Next word, then a letter

[LAMBADA](https://aclanthology.org/P16-1144/) (Paperno et al., ACL 2016) is a next-word test where the last word is easy if you read the whole passage and impossible if you only see the last sentence. From Figure 1 of the paper:

> "Yes, I thought I was going to lose the baby." "I was scared too," he stated, sincerity flooding his eyes. "You were?" "Yes, of course. Why do you even ask?" "This baby wasn't exactly planned for."
>
> **Target word:** miscarriage

Input: passage. Output: one word. Compare: exact match. Models in 2016 were under 1%. Humans got it.

[MMLU](https://arxiv.org/abs/2009.03300) (Hendrycks et al., 2020) is the quiz version. 57 subjects, four options, one letter. Hugging Face's official example from the anatomy split:

> **Question:** What is the embryological origin of the hyoid bone?
>
> **A.** The first pharyngeal arch
>
> **B.** The first and second pharyngeal arches
>
> **C.** The second pharyngeal arch
>
> **D.** The second and third pharyngeal arches
>
> **Answer:** D

Input: question. Output: `A`/`B`/`C`/`D`. Compare: did you pick D? When the paper came out, GPT-3 175B hit 43.9%. Random is 25%. The authors estimated expert humans around 89.8%. That used to be hard.

A single-shot MMLU item is one forward pass and a letter. An o1-style eval on the same item is still a letter, but the model is allowed (and trained) to spend a long private chain of thought first. You are still scoring the letter. You are not scoring a trajectory.

## Then we put the model in a repo

[SWE-bench](https://www.swebench.com/) (Jimenez et al., ICLR 2024) keeps the function, changes the scope. Input is a GitHub issue. Output is a patch. Compare is: do the tests pass?

A real item from the benchmark is `django__django-10097` ([SWE-bench](https://github.com/princeton-nlp/SWE-bench), [PR](https://github.com/django/django/pull/10097)):

> **Issue:** Make `URLValidator` reject invalid characters in the username and password
>
> URLs with un-escaped `/`, `@` or `:` characters in the username or password fields should be rejected.

You are not guessing a word. You are finding the right file in Django, writing a fix, and surviving the test suite.

At launch, Claude 2 resolved [1.96% of issues](https://arxiv.org/abs/2310.06770) with BM25 retrieval, and 4.8% if you handed it the right files. That is the "model in a repo" number. Bare completion, no agent loop.

## The harness is a different instrument

In March 2024, [Cognition's Devin](https://cognition.com/blog/swe-bench-technical-report) resolved 13.86% on a random 25% slice of SWE-bench (79 of 570). Not because someone trained a totally new base model overnight. Because the model could run commands, edit files, read the output, and try again.

A harness run is not a benchmark item. It looks more like this:

```
issue
  -> model picks a tool (bash / edit / read)
  -> environment returns stdout or a diff
  -> model tries again
  -> ...
  -> patch
  -> tests
```

You still compare with tests. But the thing you ran is a loop, not a completion. Cognition's own writeup is the point: the previous best unassisted baseline was 1.96%. Changing the scaffold moved the number to ~14%. That is a new measurement, even if the dataset is the same.

## Two years later the old test is mostly solved

In February 2025, Anthropic reported [Claude 3.7 Sonnet](https://www.anthropic.com/news/claude-3-7-sonnet) at 70.3% on SWE-bench Verified with a high-compute scaffold (parallel samples, reject patches that break visible tests, rank the rest). Without that extra scaffold, 63.7% on the same 489-task subset they could run. Two years from ~2% to ~70%.

Jason Wei has been writing for a while that [evals are the objective function](https://www.jasonwei.net/blog/evals). Yao's [second-half essay](https://ysymyth.github.io/The-Second-Half/) points at the saturation chart: old tests get crushed, then we invent a harder exam, then that gets crushed too. I'm not going to redraw someone else's figure. The story is enough. Most of the quizzes from the first half are no longer scarce.

## So score the state, not the essay

[τ-bench](https://arxiv.org/abs/2406.12045) (Yao, Shinn, Razavi, Narasimhan; Sierra) is what the second half looks like when you take it seriously. Messy human-facing work. An LLM user, a policy doc, APIs that read and write a database. You don't grade the conversation. You compare the final database to the annotated goal.

From the paper's own user instruction:

> You are mia_li_3668. You want to fly from New York to Seattle on May 20 (one way). You do not want to fly before 11am est. You want to fly in economy. You prefer direct flights but one stopover also fine. If there are multiple options, you prefer the one with the lowest price. You have 3 baggages. You do not want insurance. You want to use your two certificates to pay. If only one certificate can be used, you prefer using the larger one, and pay the rest with your 7447 card.

Input: a user who will argue with you, plus tools, plus a policy. Output: a trajectory of API calls. Compare: is the reservation in the DB what it should be?

GPT-4o still landed under 50% average success across retail and airline, and `pass^8` under 25% in retail. Capability is not reliability. The model can talk. The database is what you ship.

## Still write the stupid eval

I still believe [stupid evals](/blog/write-stupid-evals) and [error bars](/blog/report-error-bars). Start with an `assert`. Show the work. Don't overthink the framework.

I don't believe MMLU tells you if the agent you shipped can do the job. That test measures whether a function returns the right letter. Your product is a trajectory through tools and state.

The people closest to the product should write the next benchmark. If you are on the coding agent, write the issue that your users actually file. If you are on support, score the database, not the tone. The 2025 post stays up. The function never got more magical. We just started throwing bigger things at it.
