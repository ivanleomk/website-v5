I gave a talk at [Digital Jungle](http://luma.com/qdl9mr2e?tk=P3UvLA) earlier this year. Not to pitch something new, just to map the last few years of evals. I'd spent 2024 building [Manus](https://manus.im), an agent that ran multiple turns and edited real code. Before that, I wrote about [building reliable LLM applications](/blog/building-reliable-llm-applications): RAG pipelines, structured outputs, single-turn stuff. That post still holds. This is the 2026 update.

The thesis is simple: we still treat LLMs as a function (input, output, compare), but the scope of what we can throw at them changed. Evaluating a model (question in, letter out) is not evaluating an agent (trajectory, tools, environment state). We're at halftime, as Shunyu Yao put it. Scale crushed most old benchmarks. The scarce thing now is defining the right problem.

## Next-word prediction

In February 2019, OpenAI released [GPT-2](https://openai.com/index/better-language-models/) and wouldn't release the full weights. The [announcement](https://openai.com/index/better-language-models/) said they were concerned about "large language models being used to generate deceptive, biased, or abusive language at scale." The model was trained to predict the next word on 40GB of internet text. That was it. Next-word prediction.

The instruments at the time were things like LAMBADA and MMLU. [LAMBADA](https://aclanthology.org/P16-1144/) (Paperno et al., ACL 2016) tested whether a model could predict the final word of a passage when you needed the whole story to guess it. Here's a real example from the paper:

> "Yes, I thought I was going to lose the baby." "I was scared too," he stated, sincerity flooding his eyes. "You were?" "Yes, of course. Why do you even ask?" "This baby wasn't exactly planned for."  
> **Target word:** miscarriage

If you only saw the last sentence, you'd never get it. You needed the full context. State-of-the-art models in 2016 got below 1% accuracy on LAMBADA. Humans got it every time.

[MMLU](https://arxiv.org/abs/2009.03300) (Hendrycks et al., 2020) was the other pillar. It tested 57 subjects (math, law, medicine, history) with multiple-choice questions. Each question had four options, one correct answer. Here's one from the anatomy subset:

> **Question:** What is the embryological origin of the hyoid bone?  
> **A)** The first pharyngeal arch  
> **B)** The first and second pharyngeal arches  
> **C)** The second pharyngeal arch  
> **D)** The second and third pharyngeal arches  
> **Answer:** D

When MMLU came out, GPT-3 175B hit 43.9%. Random chance is 25%. The creators estimated expert humans got around 89.8%. The test was hard.

Both benchmarks measured the same thing: input a prompt, output a completion, compare the answer. The model never took an action. It never changed anything. It just predicted text.

## Putting models in repos

[SWE-bench](https://www.swebench.com/) (Jimenez et al., ICLR 2024) changed the game. Instead of asking a model to answer a question, you gave it a real GitHub issue and asked it to write a patch. The input was the issue description. The output was a code change. The comparison was running the tests.

Here's a real example from the [SWE-bench dataset](https://github.com/princeton-nlp/SWE-bench), issue `django/django#13447`:

> **Issue:** `QuerySet.in_bulk()` doesn't work with field_name='pk'  
> If `field_name='pk'` is passed to `QuerySet.in_bulk()`, the result will have the model's id in the field name (e.g. `mymodel_id`) as the key instead of `pk`.

To solve this, the model needed to find the right file in Django's codebase (thousands of lines across hundreds of files), understand how `in_bulk()` worked, write a fix, and make sure the tests passed. Not a quiz. An engineering task.

When SWE-bench launched, the best model was Claude 2 with BM25 retrieval. It solved [1.96% of issues](https://proceedings.iclr.cc/paper_files/paper/2024/file/edac78c3e300629acfe6cbe9ca88fb84-Paper-Conference.pdf) unassisted. With oracle retrieval (you give it the exact files to edit), it got to 4.8%. Still brutal.

The loop was the same (input, output, compare) but the ball was different. You weren't measuring next-word prediction anymore. You were measuring whether a model could navigate a real codebase and fix a bug.

## The harness breakthrough

In March 2024, [Cognition released Devin](https://cognition.com/blog/swe-bench-technical-report) and hit 13.86% on SWE-bench. Not a new model. A new harness. Devin could run shell commands, edit files, check outputs, retry. It had a loop. The model stayed the same (or close to it), but the scaffold around it changed everything.

This was the moment we realized that changing the scaffold is a new benchmark. You can't compare a bare model to an agent with a terminal, a file editor, and a retry budget. Different instruments. Different measurements.

Devin proved that the way you let a model interact with the world matters as much as the model itself. Two months from 2% to 14% wasn't about pretraining. It was about giving the model tools and letting it act.

## Test-time compute

In September 2024, OpenAI released [o1](https://openai.com/index/learning-to-reason-with-llms/). The hook was "thinking before you answer." The model was trained with reinforcement learning to produce a long internal chain of thought before responding. Not prompted. Trained.

The big insight: accuracy scales with test-time compute. Give o1 more time to think and it gets better. [The relationship is roughly log-linear](https://vibeengines.com/paper/o1-system-card): every time you double the compute, accuracy goes up by a fixed amount. A new scaling law, but at inference time instead of training time.

o1 ranked in the 89th percentile on Codeforces (competitive programming) and solved 83% of problems on the AIME math qualifier (vs. 13% for GPT-4o). Same loop: input a problem, output a solution, compare. Different axis: you scaled compute at inference, not training.

## Two years from 2% to 70%

In February 2025, Anthropic released [Claude 3.7 Sonnet](https://www.anthropic.com/news/claude-3-7-sonnet) and reported 70.3% on SWE-bench Verified, a cleaner 500-task subset of SWE-bench. Two years earlier, Claude 2 solved ~2% of issues. Now: 70%.

To be clear, the 70.3% number uses a high-compute setup: parallel sampling, rejection sampling against visible tests, and a ranking model to pick the best solution. Without that scaffold, Claude 3.7 Sonnet gets 63.7%. Still massive. Still real.

This is the trajectory. From 2% to 70% in two years. Models got better. Harnesses got smarter. Test-time compute became a thing. Progress compounded.

[Jason Wei's chart](https://www.jasonwei.net/blog/common-arguments-regarding-emergent-abilities) on AI benchmark saturation showed this pattern across dozens of tests: as models scaled, old benchmarks saturated. Tasks that looked impossible in 2020 became trivial by 2024. SWE-bench held longer because it was harder, but even it is cracking.

## Halftime

Most old tests are solved or close to it. MMLU used to be the standard. Now it's a checkbox. The scarce thing isn't compute or data anymore. It's defining the right problem. What should we measure?

[τ-bench](https://arxiv.org/abs/2406.12045) (Yao et al., 2024, Sierra) is one answer. Instead of a single-turn quiz, τ-bench simulates a customer service conversation. An agent talks to a user (simulated by another LLM), uses APIs to read and write a database, and follows a policy document. Success isn't judged by the conversation transcript. It's judged by the final database state.

Here's a task from the [airline domain](https://github.com/sierra-research/tau-bench):

> You are `mia_li_2017`, and you want to change your most recent flight to fly to SF instead of LA on the same day. If the change is not possible, you want the agent to cancel and rebook.

The agent has to:
1. Look up the booking
2. Check if the flight change is available
3. Follow the policy (maybe there's a fee, maybe it's not allowed)
4. Update the database or cancel and rebook
5. Confirm with the user

At the end, τ-bench compares the database state to the expected outcome. Did the agent do the right thing? Not "did it say the right words," but "did the right thing happen."

Even GPT-4o, the best model at the time, succeeded on less than 50% of tasks. The pass^k metric (did it solve the task on all k independent trials) was even worse: under 25% in the retail domain. Reliability, not just capability.

This is the shift. We're not measuring whether a model can answer a question anymore. We're measuring whether an agent can complete a messy, multi-turn, human-facing task and leave the world in the right state.

## The loop stayed the same

I still believe in [stupid evals](/blog/write-stupid-evals) and [error bars](/blog/report-error-bars). Start simple. Measure what matters. Report uncertainty.

But I don't believe MMLU tells you if your agent can do the job. That test measures world knowledge. Agents need to navigate state, follow rules, recover from mistakes, and act reliably over many turns. Different ball.

The people closest to the product should write the next benchmark. If you're building a coding agent, write evals that test what real users need: can it refactor a module without breaking tests? Can it debug a flaky integration? If you're building a customer service agent, test the database state, not the prose.

The loop never changed: input, output, compare. But the ball changed. Evaluating agents is not evaluating models. We're at halftime. The scarce thing now is defining the right problem.
