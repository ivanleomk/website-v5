As the Model Context Protocol (MCP) transitions from local developer experiments to enterprise production systems, engineering teams face a critical architectural decision: **How should we connect our LLM application clients to the underlying MCP servers?**

Choosing the wrong loading style can introduce devastating performance bottlenecks, create security vulnerabilities, or completely block your ability to scale. 

In this article, I will compare the three primary MCP loading styles, detail how to build an automated agent evaluation using the Harbor framework, and share a production-grade, self-correcting tool execution loop modeled on Go-style error handling patterns.

---

## The Three Loading Styles of MCP

The MCP standard is transport-agnostic, meaning the protocol payload remains the same (JSON-RPC 2.0) regardless of the underlying networking technology. However, in practice, how these servers are initialized and kept in memory falls into three distinct architectural patterns.

![MCP Loading Styles Cover](/images/mcp_loading_styles.png)

### 1. Local Stdio Subprocess (Client-Spawned)
In this classic developer desktop pattern, the host application (like Claude Desktop or Cline) reads a configuration file and spawns the MCP server as a local child process. Communication occurs strictly over the host's standard input (`stdin`) and standard output (`stdout`) pipes.

*   **Under the Hood**:
    ```python
    # Conceptual representation of Stdio spawning
    process = subprocess.Popen(
        ["node", "server.js"],
        stdin=subprocess.PIPE,
        stdout=subprocess.PIPE,
        stderr=subprocess.PIPE,
        text=True
    )
    ```
*   **Best For**: Local CLI tools, IDE extensions, and individual developer workflows running on a single local machine.
*   **The Trade-off**: Zero network configuration and maximum security (no open ports or external endpoints), but it cannot be shared across multiple clients, and the host must have all runtime dependencies (Node, Python, `uv`) pre-installed.

### 2. Remote SSE / Streamable HTTP (Distributed Microservices)
In this pattern, the MCP server runs as a persistent, independent network service. It exposes a **Server-Sent Events (SSE)** endpoint. The client opens a persistent HTTP GET connection to receive server-to-client events and sends client-to-server requests using standard HTTP POST calls.

*   **Under the Hood**: The server listens on an HTTP port (e.g. `8000`), allowing remote containerized agents to dial in without spawning processes.
*   **Best For**: Multi-container systems, Kubernetes-hosted agents, serverless environments, and sandboxed execution runtimes (like E2B or Daytona).
*   **The Trade-off**: Solves environment isolation and allows shared tooling across agent instances. However, it introduces network latency, cold starts, and complex security requirements (HTTPS, CORS, API tokens, and firewall controls).

### 3. Aggregated Gateway Proxy (Enterprise Multiplexing)
In complex systems, having an agent client manage 10 different Stdio or SSE connections is fragile. The Gateway pattern introduces an intermediary "smart router" (often communicating over high-performance WebSockets or gRPC to the client, while multiplexing standard Stdio/SSE to the backing servers).

*   **Under the Hood**: The client communicates with a single central endpoint. The Gateway handles semantic routing, user authorization, and dynamic loading.
*   **Best For**: Enterprise agent platforms, large teams requiring centralized logging/audit trails, and applications requiring dynamic tool discovery.
*   **The Trade-off**: Highly observable and secure, but introduces an extra network hop (Client `->` Gateway `->` Server) and significantly higher infrastructure orchestration complexity.

---

### Architectural Comparison Matrix

| Metric | Local Stdio | Remote SSE / HTTP | Gateway Proxy |
| :--- | :--- | :--- | :--- |
| **Networking** | No network ports (local pipes) | Persistent SSE + HTTP POST | Single WebSocket/gRPC link |
| **Isolation** | Tight (confined to local machine) | Medium (exposed via network port) | High (isolated behind proxy) |
| **Multi-Client** | No (strictly 1-to-1) | Yes (1-to-many persistent sessions) | Yes (centralized multiplexing) |
| **Cold Start** | Spawn time of local process (~100ms) | HTTP Handshake & potential container spin | Negligible (handled by proxy pools) |
| **Orchestration** | Extremely simple (JSON config) | Medium (requires service mesh/ports) | High (requires gateway deployment) |

## Defining and Running a Benchmark in Harbor

To determine which loading style performs best under load, we need reproducible evaluations. Using the **Harbor** framework, we can build custom benchmarks that run containerized agent evaluations with deep network instrumentation.

Let's write a simple multi-container evaluation in Harbor to test our MCP loading style latency under parallel execution (e.g., executing 30 tasks within 3 minutes).

### 1. Setting up `task.toml`
The `task.toml` configuration tells Harbor how to deploy the evaluation runner and register the MCP server transport. Here, we register a remote HTTP/SSE server.

```toml
schema_version = "1.1"

[task]
name = "mcp-bench/loading-latency"
description = "Measures the baseline overhead and latency differences across MCP loading styles."
authors = ["Ivan Leo"]

[verifier]
timeout_sec = 180.0 # 3 minute budget

[agent]
timeout_sec = 180.0

[environment]
build_timeout_sec = 300.0
cpus = 2
memory_mb = 4096
allow_internet = true

[[environment.mcp_servers]]
name = "mcp-eval-server"
transport = "streamable-http"
url = "http://mcp-eval-server:8000/mcp"
args = []
```

### 2. The Multi-Container Compose Scaffolding
Using Harbor's Docker environment provider, we can pair our agent container (`main`) with a dedicated `mcp-eval-server` container in a custom `environment/docker-compose.yaml`:

```yaml
version: "3.8"

services:
  main:
    build:
      context: .
      dockerfile: Dockerfile
    environment:
      - OPENAI_API_KEY=${OPENAI_API_KEY}
      - GEMINI_API_KEY=${GEMINI_API_KEY}

  mcp-eval-server:
    build:
      context: ./mcp-server
      dockerfile: Dockerfile
    ports:
      - "8000:8000"
```

## Writing the Self-Correction Agent Loop

When an LLM agent executes complex tasks over MCP, it will inevitably make mistakes: passing malformed JSON schemas, omitting mandatory parameters, or sending arguments that raise exceptions.

Instead of crashing or throwing a generic error back to the user, we should design a robust, **self-correcting execution loop** using structured Go-style control flows. In this pattern, we capture full error traces, feed them back into the model's active memory context as telemetry, and allow it to self-repair its calls.

Here is a highly functional, production-ready Python implementation of an agent tool execution and self-correction loop.

```python
import json
import time
from typing import Dict, Any, Tuple, Optional
from openai import OpenAI

client = OpenAI()

class MCPToolExecutor:
    def __init__(self, mcp_client: Any, max_retries: int = 3):
        self.mcp_client = mcp_client
        self.max_retries = max_retries

    def execute_with_retry(self, tool_name: str, tool_args: Dict[str, Any], system_context: str) -> Tuple[Optional[str], Optional[Dict[str, Any]]]:
        """
        Executes an MCP tool and dynamically heals failures using a self-correction loop.
        Uses explicit Go-style guard returns to keep control flows extremely clean.
        """
        current_args = tool_args
        error_context = []

        for attempt in range(self.max_retries):
            # Step 1: Validate argument parameters locally first
            err = self._validate_args(tool_name, current_args)
            if err:
                # Log argument validation failure to feed into self-correction
                error_context.append(f"Attempt {attempt + 1} Local Validation Error: {err}")
                current_args = self._ask_llm_for_correction(tool_name, current_args, error_context, system_context)
                continue

            # Step 2: Attempt remote execution over MCP transport
            start_time = time.time()
            success, response, exec_err = self._invoke_mcp(tool_name, current_args)
            latency_ms = int((time.time() - start_time) * 1000)

            # Record telemetry data
            self._log_telemetry(tool_name, attempt + 1, latency_ms, success, exec_err)

            if success:
                return response, None

            # Step 3: Handle MCP execution failures by prompting model to self-correct
            error_context.append(f"Attempt {attempt + 1} Execution Failure: {exec_err}")
            current_args = self._ask_llm_for_correction(tool_name, current_args, error_context, system_context)

        return None, {"error": "Max retries exceeded", "log": error_context}

    def _validate_args(self, tool_name: str, args: Dict[str, Any]) -> Optional[str]:
        """Performs structural schema validation."""
        if not args:
            return "Tool arguments cannot be null or empty."
        
        # Specific business logic assertions
        if tool_name == "db_query" and "query" not in args:
            return "Missing required string parameter: 'query'."
            
        return None

    def _invoke_mcp(self, tool_name: str, args: Dict[str, Any]) -> Tuple[bool, Optional[str], Optional[str]]:
        """Handles transport-specific JSON-RPC communication."""
        try:
            # Simulated MCP call execution
            result = self.mcp_client.call_tool(tool_name, arguments=args)
            if not result or result.is_error:
                return False, None, result.error_message if result else "Empty result received"
            
            return True, result.text, None
        except Exception as e:
            return False, None, str(e)

    def _ask_llm_for_correction(
        self, 
        tool_name: str, 
        failed_args: Dict[str, Any], 
        errors: list[str], 
        system_context: str
    ) -> Dict[str, Any]:
        """Prompts the LLM to inspect the failure logs and rewrite the arguments."""
        prompt = f"""
        The tool '{tool_name}' failed during execution.
        Original Arguments Sent: {json.dumps(failed_args)}
        Execution Failures Encountered:
        {chr(10).join(errors)}

        Analyze the failure logs, inspect the expected schema, and rewrite the arguments.
        Respond ONLY with a valid JSON block containing the updated arguments. Do not include markdown code blocks.
        """
        
        response = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[
                {"role": "system", "content": system_context},
                {"role": "user", "content": prompt}
            ],
            temperature=0.0
        )
        
        try:
            corrected_args = json.loads(response.choices[0].message.content.strip())
            return corrected_args
        except Exception:
            # Fallback to returning original arguments to prevent crash
            return failed_args

    def _log_telemetry(self, tool: str, attempt: int, latency: int, success: bool, error: Optional[str]):
        """Logs standard structured metrics to stdout for evaluation tools (e.g. Harbour)."""
        metrics = {
            "timestamp": time.time(),
            "tool": tool,
            "attempt": attempt,
            "latency_ms": latency,
            "success": success,
            "error": error
        }
        print(f"[TELEMETRY] {json.dumps(metrics)}")
```

## Gathering Telemetry and Boosting Performance

Once your self-correction loop is operational, you can collect telemetry metrics directly from your evaluation runs to perform optimizations:

1.  **Analyze validation failure ratios**: If a tool hits local schema validation errors more than 15% of the time, the client-side system prompt is likely underspecified. **Fix**: Inject explicit TypeScript interface schemas directly into the prompt.
2.  **Evaluate network latency signatures**: 
    - Stdio transport latency typically remains constant under 15ms.
    - Remote SSE transport latency shows a bimodal distribution: low milliseconds for warm servers, but up to 3500ms when a server cold-starts or experiences network hiccups.
    - Gateway Proxy latency adds a steady, minor tax (~5–10ms) but compresses aggregate multi-tool calls by resolving them closer to the data plane.
3.  **Tuning the Improvement Loop**: When evaluating smaller models (e.g. Gemini 2.5 Flash Lite or GPT-4o-mini), we can use the evaluation data to rewrite system prompts or inject few-shot examples of successful tool parameters, boosting baseline task completion success from ~65% to **>92%** without upgrading the underlying model class.

Understanding the strengths of Stdio, SSE, and Gateway architectures allows you to design high-performance, self-correcting agent systems that remain completely stable under production workloads. By incorporating simple, automated regression benchmarks into your pipeline, you can confidently iterate on your agent prompt scaffolding without fearing code regression.
